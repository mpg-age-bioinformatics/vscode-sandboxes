# Bioinformatics sandbox execution policy

- Store implementation files, notebooks, tests, Dockerfiles, Compose files, and dependency manifests under `code/`. Store input data, intermediate data, caches, results, figures, and run logs under `data/`.
<!-- bioinformatics-sandbox:scientific-libraries:start -->
- Prefer Python for bioinformatics work, followed by R and Bash when better suited. Scientific analysis, tabular-data handling, statistics, and visualization must use established scientific or domain libraries such as NumPy, SciPy, Pandas, Matplotlib, Seaborn, Biopython, scikit-learn, Bioconductor, and appropriate specialist tools. Adding and containerizing the appropriate dependencies is part of the task; their absence is never a reason to replace a conventional scientific workflow with hand-written standard-library code.
- For a CSV-backed heatmap, ordinarily create or read the table with Pandas and render it with Seaborn and Matplotlib using a direct `sns.heatmap(...)` call. Include meaningful row and column labels, a color bar, an appropriate palette and scaling, layout adjustment, and a conventional saved figure such as PNG, SVG, or PDF under `data/`. Do not manually parse CSV, interpolate colors, construct SVG/XML, or implement heatmap cells and legends yourself unless the user explicitly requests a dependency-free or hand-built renderer.
- In interactive analysis requests, wording such as “make me a heatmap” or “write me a function for a heatmap” normally asks for executable analysis code using the library function and all supporting code. Do not introduce a new wrapper with `def` unless the user explicitly asks for a named, custom, or reusable Python function, or reuse is clearly required.

- This repository is developed inside a Docker Sandbox microVM. Do not create or use a VS Code Dev Container, Docker-in-Docker Dev Container, or host Docker-socket mount.
- Run code directly in the Docker Sandbox when it needs only tools already present and no additional runtime isolation. When code needs project-specific packages, system dependencies, a service, a distinct runtime, or a reproducible scientific environment, create a Dockerfile and dependency manifest under `code/`, then build and run a workload container on the sandbox's private Docker daemon. For example, if Pandas, Matplotlib, or Seaborn is unavailable for a requested heatmap, add those pinned dependencies and run the analysis in a workload container rather than falling back to a custom SVG generator.
- Never install project dependencies ad hoc as a substitute for recording the environment. Track every installation instruction. Pin direct dependencies and workload base images to exact versions or immutable digests, and commit supported lockfiles alongside their manifests.
- Keep Docker build contexts narrow, copy only required files, avoid secrets in images, and use a non-root workload user when compatible. Mount only required project paths; mount inputs read-only when practical and grant write access only to the needed output paths.
- Give verified workload containers stable explicit names and retain them when exact `docker exec` reproduction is useful. Capture stdout and stderr in a version-matched log under `data/`. In the final response, provide the actual build and run or start/exec commands needed to reproduce executed work.
- Maintain an exact eight-character lowercase hexadecimal `CODE_VERSION` in output-generating source. Update it once per coherent implementation change and include it immediately before every generated output extension, such as `summary.a1b2c3d4.csv`. Do not overwrite outputs from another code version.
- Treat the mounted repository as the only host path in scope. Do not inspect or mount additional host paths, credentials, or sockets unless the user explicitly authorizes them.
